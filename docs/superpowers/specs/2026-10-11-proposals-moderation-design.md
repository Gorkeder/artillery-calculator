# Предложения пользователей и модерация (этап B) — дизайн

Дата: 2026-10-11. Статус: на ревью.

Продолжает спеки [карты](2026-10-11-interactive-map-editor-design.md), [аккаунтов](2026-10-11-user-accounts-design.md)
и [личных меток](2026-10-11-personal-marks-design.md) (этап C, уже на проде).

## Цель

Вошедший пользователь предлагает на общую карту новые объекты (точка, полигон, линия) и сообщает об ошибках в
существующих. Админ рассматривает их в очереди: одобряет (объект становится общим) или отклоняет с причиной.
Автор видит статус на карте. Админ может заблокировать автора для предложений и жалоб.

## Решения (согласовано)

| Вопрос | Решение |
|--------|---------|
| Что можно предложить | Только **новые** объекты в существующую категорию. Правок и удалений чужих общих объектов нет |
| Жалобы | У любого общего объекта кнопка «Сообщить об ошибке» (текст до 500 символов), без прямой правки. Админ чинит сам |
| Обратная связь автору | Статус и причина на карте («На модерации», «Отклонено: причина»), писем нет |
| Фото | В предложениях **нет**; админ добавляет их сам после одобрения |
| Блокировка автора | Только предложения и жалобы. Вход и личные метки работают. Ожидающие предложения автора отклоняются автоматически, блокировку можно снять |
| Хранение | Строки `features` со статусом `pending` (как задумано в спеке карты), а не отдельная таблица |

### Почему `features`, а не отдельная таблица

`author_id` и `status` заложены в спеке карты именно под это: `listFeatures` уже отдаёт автору его `pending`,
`can()` принимает `resource`. Пайплайн показа и редактор переиспользуются. Недостаток: отклонённое
представлено как `pending` с заполненным `reject_reason` (изменить `CHECK` статуса в SQLite
означает пересоздание таблицы с внешними ключами, это дороже пользы). Состояния описаны ниже одной таблицей.

## Состояния объекта

| Состояние | `status` | `reject_reason` | Кто видит |
|-----------|----------|-----------------|-----------|
| Опубликован | `approved` | `NULL` | все |
| На модерации | `pending` | `NULL` | автор и админ |
| Отклонён | `pending` | текст причины | автор и админ |

Переходы: создание пользователем → «На модерации»; админ: «На модерации» → «Опубликован» (`approve`) или
«Отклонён» (`reject`, причина 1..200 символов); «Отклонён» → «Опубликован» (админ передумал). «Опубликован» в
«Отклонён» не переходит (409). Одобрение очищает `reject_reason`. Отклонённые объекты старше 30 дней
(`reviewed_at`) удаляются ежечасной очисткой, которая уже есть в `server/index.js` (`cleanup`).

## Модель данных

Миграция 4 (`MIGRATIONS` в `server/db.js`):

```sql
ALTER TABLE features ADD COLUMN reject_reason TEXT;
ALTER TABLE features ADD COLUMN reviewed_at TEXT;
ALTER TABLE features ADD COLUMN reviewed_by INTEGER REFERENCES users(id) ON DELETE SET NULL;
ALTER TABLE users ADD COLUMN proposals_blocked_at TEXT;
ALTER TABLE users ADD COLUMN proposals_block_reason TEXT;
CREATE TABLE reports (
  id INTEGER PRIMARY KEY,
  feature_id INTEGER NOT NULL REFERENCES features(id) ON DELETE CASCADE,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  text TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  resolved_at TEXT,
  resolved_by INTEGER REFERENCES users(id) ON DELETE SET NULL
);
CREATE INDEX idx_reports_open ON reports(resolved_at, feature_id);
CREATE UNIQUE INDEX idx_reports_one_open ON reports(feature_id, user_id) WHERE resolved_at IS NULL;
CREATE INDEX idx_features_status ON features(status, reviewed_at);
```

Пользователя `users.proposals_blocked_at IS NOT NULL` считаем заблокированным.

## Права

`server/permissions.js`, новые действия:

- `feature:propose`: любой вошедший пользователь, у которого `proposals_blocked_at IS NULL`;
- `report:create`: то же;
- `feature:update` для не-админа: только если `resource.author_id === user.id`, `resource.status === 'pending'`
  и `resource.reject_reason === null`; для админа как раньше;
- `feature:delete` для не-админа: только если `resource.author_id === user.id` и `resource.status === 'pending'`
  (включая отклонённые); для админа как раньше;
- модерация (`moderation:read`, `moderation:write`): только админ.

`can()` получает пользователя вместе с признаком блокировки: `getSessionUser` (`server/auth.js`) добавляет
`proposalsBlocked` к объекту пользователя (по `users.proposals_blocked_at`), чтобы проверка шла в одном месте.

`GET /api/me`: в `can` добавляется `propose: boolean` (вошедший и не заблокирован); поля `map/category/feature`
остаются «только админ»; в `user` добавляется `proposalsBlocked: boolean` и, если заблокирован, `blockReason`.

## API

Все маршруты записи требуют сессию и `X-Requested-With`, как остальные.

### Пользователь

| Запрос | Тело | Поведение |
|--------|------|-----------|
| `POST /api/features` | как сейчас (`map_id`, `category_id`, `geometry`, `title`, `description`) | У не-админа создаёт `pending`. Поля `color`/`opacity` игнорируются. Заблокирован → 403 `proposals_blocked`. Лимит → 409 `proposals_limit` |
| `PATCH /api/features/:id` | как сейчас | Не-админу: только свой неотклонённый `pending`, иначе 404. `color`/`opacity` игнорируются |
| `DELETE /api/features/:id` | — | Не-админу: только свой `pending` (в том числе отклонённый), иначе 404 |
| `POST /api/features/:id/report` | `{text}` (1..500) | Жалоба на **опубликованный** объект. Не опубликован → 404. Вторая открытая жалоба на тот же объект от того же пользователя → 409 `report_exists`. Лимит → 409 `reports_limit`. Заблокирован → 403 `proposals_blocked` |

Чужой, несуществующий и недоступный по состоянию объект в `PATCH`/`DELETE` отвечает одинаково: **404**.
Загрузка фото (`/api/features/:id/images`) остаётся только для админа.

### Публичная выдача

`GET /api/maps/:slug`: поле `author_id` в объектах отдаётся **только админу**; остальным вместо него приходит
`mine: boolean` (автор запрашивающего), чтобы публичный ответ не раскрывал числовые id пользователей. Добавляются
`reject_reason` (только автору и админу) и `status` (как сейчас). Права просмотра прежние: чужие `pending`
невидимы никому, кроме админа.

### Админ

| Запрос | Тело | Поведение |
|--------|------|-----------|
| `GET /api/moderation` | — | `{ proposals: [...], reports: [...], blocked: [...] }`: ожидающие неотклонённые предложения (с логином автора, картой и категорией), нерешённые жалобы (с объектом и автором жалобы), заблокированные авторы |
| `POST /api/features/:id/approve` | — | Делает объект опубликованным (из «На модерации» или «Отклонён»), заполняет `reviewed_*`. Не `pending` → 409 |
| `POST /api/features/:id/reject` | `{reason}` (1..200) | «На модерации» → «Отклонён». Опубликованный → 409 |
| `POST /api/users/:id/block-proposals` | `{reason?}` (≤ 200) | Ставит блокировку; все неотклонённые `pending` автора отклоняются с причиной «Автор заблокирован». Админа и самого себя блокировать нельзя (400) |
| `POST /api/users/:id/unblock-proposals` | — | Снимает блокировку; отклонённые не восстанавливаются |
| `POST /api/reports/:id/resolve` | — | Помечает жалобу решённой (`resolved_at`, `resolved_by`) |

Одобрение, отклонение и блокировка идут одной транзакцией.

## Лимиты

| Что | Значение | Результат |
|-----|----------|-----------|
| Неотклонённых ожидающих предложений на пользователя | 10 | 409 `proposals_limit` |
| Открытых жалоб на пользователя | 20 | 409 `reports_limit` |
| Открытая жалоба на объект от одного пользователя | 1 | 409 `report_exists` |
| Запросы записи (предложения и жалобы) | 60 за 10 минут на пользователя (`proposalsWrite` в `server/app.js`) | 429 |
| Текст жалобы | до 500 символов | 400 |
| Причина отклонения | 1..200 символов | 400 |

## Интерфейс

- **Режимы редактора.** Переключатель режимов (из этапа C) показывается всем вошедшим на ПК:
  у админа «Общие / Мои метки» (как сейчас); у пользователя «Предложить / Мои метки», по умолчанию «Мои метки»
  (приватный режим безопаснее). Режим «Предложить» — это тот же `MapEditor` в упрощённом виде:
  инструменты точка/полигон/линия, выбор категории из списка слева, панель свойств с названием и описанием;
  без менеджеров категорий и карт, без цвета, прозрачности и фото.
- **Статус на карте.** Свои ожидающие и отклонённые объекты видны автору в обычных слоях категории с пунктирным
  контуром и пометкой в карточке: «На модерации» или «Отклонено: причина». Отклонённый можно удалить.
- **Жалоба.** В карточке опубликованного объекта вошедшему не заблокированному пользователю доступна кнопка
  «Сообщить об ошибке» (поле до 500 символов, «Отправить»). Гостю — подсказка войти.
- **Блокировка.** Заблокированный видит в панели редактора «Отправка предложений для вас закрыта» и не может
  использовать режим «Предложить»; кнопка жалобы скрыта.
- **Модерация (админ).** Кнопка «Модерация» в панели редактора открывает диалог (`map-editor-dialogs.js`,
  `MapEditorDialogs.moderation()`) с вкладками «Предложения», «Жалобы», «Заблокированные». В предложении:
  логин автора, карта, категория, название, описание, кнопки «Показать на карте», «Одобрить», «Отклонить»
  (запрашивает причину), «Заблокировать автора». В жалобе: объект, автор жалобы, текст, «Показать на карте»,
  «Решено». В блокировке: логин, причина, «Разблокировать». Счётчик ожидающих рядом с кнопкой.
- Пользовательский текст везде через `textContent`. На телефоне редактора предложений нет (как у остальных
  редакторов), но свои предложения со статусом видны, а кнопка жалобы доступна.

## Приватность

- Публичный ответ карты не содержит `author_id`; автор объекта на карте не показывается.
- Жалоба хранит `user_id`, автор жалобы виден только админу.
- `proposals_block_reason` виден заблокированному пользователю (в `/api/me`) и админу.
- `privacy.html` дополняется абзацем: предложения и жалобы хранятся с привязкой к аккаунту, видны автору и
  администратору, одобренные объекты становятся общими и остаются после удаления аккаунта без привязки к нему
  (`author_id` обнуляется существующим `ON DELETE SET NULL`).

## Тестирование

`node --test`, новый файл `server/test/proposals.test.js` плюс обновление ожиданий существующих тестов `can`:

- миграция 4 на базе версии 3 сохраняет данные;
- права: пользователь создаёт `pending`, правит только свой неотклонённый, удаляет свой `pending`; чужое и
  опубликованное → 404; админ правит и удаляет всё; заблокированный → 403;
- поля `color`/`opacity`, `status`, `author_id`, `reject_reason` в теле от пользователя игнорируются;
- очередь `GET /api/moderation` доступна только админу (401/403 иначе);
- одобрение, отклонение (причина обязательна, длина), повторное одобрение, отклонение опубликованного → 409;
- блокировка: ожидающие предложения автора отклоняются, личные метки и вход работают, новое предложение → 403,
  разблокировка снимает запрет, себя и админа блокировать нельзя;
- публичный ответ не содержит `author_id` и чужих `pending`; автору приходят его `pending` и `mine: true`;
- жалоба: на опубликованный объект 201, на `pending` 404, повторная 409, лимиты, длина, заблокированный 403;
- лимиты: 10 ожидающих → 409, частота записи → 429;
- каскады: удаление объекта удаляет жалобы, удаление пользователя удаляет его жалобы и обнуляет `author_id`;
- очистка удаляет отклонённые старше 30 дней и не трогает остальные.

Фронтенд — ручной чек-лист: гость; пользователь на ПК (предложение, правка, удаление, отклонённое, жалоба,
блокировка); админ (очередь, одобрение, отклонение, блокировка и разблокировка, переключатель режимов);
375 px (жалоба доступна, редактора нет); два пользователя не видят предложений друг друга.

## Раскатка

1. Бэкап БД, затем деплой (миграция 4 выполняется при старте `anoma-api`, как миграции 2 и 3).
2. Порядок коммитов в ветке: миграция и права, затем API, затем интерфейс.
3. Проверка на проде: новый тестовый пользователь предлагает точку, админ одобряет, точка видна второму
   пользователю, жалоба видна в очереди, блокировка закрывает предложения.
4. Обновить `CLAUDE.md` («Сделано», «Не сделано»), `RELEASE.md`, `privacy.html`.

## Вне объёма

Фото в предложениях; предложения правок и удаления существующих общих объектов; письма и уведомления;
история изменений и откат; массовые действия в очереди; полный бан аккаунта; рейтинг авторов и автоодобрение.
