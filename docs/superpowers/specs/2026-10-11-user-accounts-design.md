# Аккаунты обычных пользователей — дизайн (этап A)

Дата: 2026-10-11. Статус: реализовано в ветке `user-accounts`, не выкачено на прод (текст приведён к реализации).

## Контекст и цель

На сайте ANOMA WIKI есть карта `/map` с редактором только для админа (спек
`2026-10-11-interactive-map-editor-design.md`). Нужны аккаунты для обычных посетителей.
Итоговая цель — три возможности, которые строятся на аккаунтах:

| Этап | Что | Порядок |
|------|-----|---------|
| **A** | Аккаунты: регистрация, вход, почта, сброс и смена пароля, сессии, профиль | первым (этот документ) |
| C | Личные метки: приватные точки и заметки, видны только владельцу | вторым |
| B | Предложения точек с модерацией (`pending` → одобрено/отклонено) | третьим |

Этот спек описывает только этап A. C и B получают свои спеки и планы. Для них оставляется место в `can()`,
`capabilities()` и `featureFilter()`, но поведение для роли `user` сейчас не меняется: редактор карты ей не доступен.

## Принятые решения

| Вопрос | Решение |
|--------|---------|
| Идентичность | Логин (публичный ник) + почта (приватная) + пароль |
| Вход | По логину или по почте. Только после подтверждения почты |
| Защита от ботов | Лимиты по IP, по почте и по аккаунту, скрытое поле-ловушка. Без капчи |
| Почта | Свой отправитель с домена `anoma-wiki.ru` через внешний SMTP (порт 465, TLS) |
| Зависимости | Без npm. Свой минимальный SMTP-клиент на `node:tls` |
| Токены | Таблица `auth_tokens` в SQLite, хранится только хеш, одноразовые |
| В v1 | Подтверждение почты, сброс пароля, смена пароля, список сессий |
| Не в v1 | Смена почты, самостоятельное удаление аккаунта, соцсети, 2FA, аватары, баннер cookie |

## Данные и миграция

### `users`: новые колонки
- `email` TEXT. Уникальный индекс по `lower(email)`. У админа может быть `NULL`.
- `email_verified_at` TEXT. `NULL` означает «не подтверждена», вход запрещён.
- `password_changed_at` TEXT.

Дополнительно: уникальный индекс `idx_users_login_lower` по `lower(login)`, чтобы `Admin` и `admin` не были
разными аккаунтами. Если на проде такое пересечение есть, миграция падает громко (на проде сейчас один `admin`).

### `sessions`: новые колонки
`created_at` INTEGER (мс), `last_seen_at` INTEGER (мс), `ip` TEXT, `user_agent` TEXT (до 200 символов).
Идентификатор сессии для UI и `DELETE /api/sessions/:id` — первые 16 hex-символов `token_hash`; поиск всегда
с условием `user_id = текущий пользователь`.

### `auth_tokens` (новая)

| поле | |
|---|---|
| `token_hash` TEXT PK | sha256 токена; сам токен только в письме |
| `user_id` INTEGER | `REFERENCES users(id) ON DELETE CASCADE` |
| `kind` TEXT | `verify_email` или `reset_password` |
| `expires_at` INTEGER | мс. Подтверждение — 24 ч, сброс — 1 ч |
| `used_at` INTEGER | мс или `NULL` |

Выпуск нового токена того же `kind` для пользователя помечает прежние неиспользованные как использованные.

### Миграции
`db.js` получает версию схемы через `PRAGMA user_version` и упорядоченный список шагов; каждый шаг выполняется
один раз в транзакции при `openDb`. Версия 1 — текущая схема. Версия 2 — этот спек. Для существующих строк
`users` миграция ставит `email_verified_at = created_at`, чтобы `admin` продолжил входить. Перед первым деплоем
вручную снимается бэкап БД (cron делает это ежедневно, но перед миграцией — отдельно).

### Очистка
При старте и затем раз в час: удаляются просроченные и использованные токены старше суток, а также
неподтверждённые пользователи с `created_at` старше 24 ч, у которых нет живого неиспользованного токена
`verify_email`. Освобождаются их логин и почта.

## API

Файл `server/routes/account.js`. Существующие `GET /api/me`, `POST /api/login`, `POST /api/logout` остаются
по тем же путям. `X-Requested-With` обязателен на любых не-GET запросах (как сейчас).

### Публичные

| Запрос | Тело | Поведение |
|---|---|---|
| `POST /api/register` | `login, email, password, consent, website` | Валидирует, создаёт неподтверждённого `user`, отправляет письмо. `consent` должно быть `true`, иначе 400 `consent_required` (согласие на обработку данных проверяется и на сервере). `website` непустое — ответ как при успехе, но ничего не создаётся |
| `POST /api/verify-email` | `token` | Одноразово подтверждает почту, создаёт сессию и ставит cookie |
| `POST /api/resend-verification` | `email` | Новое письмо подтверждения, ответ всегда одинаковый |
| `POST /api/forgot-password` | `email` | Письмо со ссылкой сброса, ответ всегда одинаковый |
| `POST /api/reset-password` | `token, password` | Меняет пароль, закрывает все сессии пользователя, помечает почту подтверждённой (владение почтой доказано токеном). Сессию не создаёт |
| `POST /api/login` | `login, password` | `login` с символом `@` трактуется как почта (в логине `@` запрещён). Неподтверждённому — ошибка `email_not_verified`, только при верном пароле |

### Для вошедшего

| Запрос | Поведение |
|---|---|
| `POST /api/change-password` `{current, next}` | Проверяет текущий пароль, меняет, закрывает все остальные сессии, текущая остаётся |
| `GET /api/sessions` | Список своих сессий: отпечаток, ip, user_agent, created_at, last_seen_at, признак `current` |
| `DELETE /api/sessions/:id` | Завершает одну свою сессию |
| `POST /api/sessions/revoke-others` | Завершает все, кроме текущей |

`GET /api/me` дополнительно возвращает `email` и `emailVerified` для самого пользователя.

### Правила

- **Единые ответы.** `forgot-password`, `resend-verification` и `register` с уже занятой почтой отвечают
  одинаково («если адрес известен, письмо отправлено»). Если почта занята неподтверждённым аккаунтом, ему
  повторно отправляется письмо подтверждения (в пределах лимитов). Занятый логин сообщается явно.
- **Порядок проверок при регистрации.** Honeypot `website`; поля (логин, почта, пароль) и `consent`; затем лимиты
  (`registerIp` считается только после проверки полей, чтобы кривые запросы не жгли лимит), `registerEmail` и
  лимиты писем; затем scrypt; затем проверка занятого логина (`login_taken`) **до** поиска по почте — иначе
  ответ на занятый логин зависел бы от того, зарегистрирована ли почта; затем поиск по почте.
- **Вход неподтверждённого.** `email_not_verified` возвращается только при верном пароле; при неверном —
  обычный 401 «invalid login or password».
- **Время ответа.** Ветки «почта занята» и «почты нет» одинаково дорогие: scrypt считается в обоих случаях,
  как уже сделано для `DUMMY_HASH`.
- **Пароль:** 8–128 символов, не равен логину.
- **Логин:** `[A-Za-z0-9_.-]{3,32}`, уникальность без учёта регистра. Зарезервированы:
  `admin`, `administrator`, `moderator`, `support`, `root`, `system`, `anoma`.
- **Почта:** приведение к нижнему регистру, до 254 символов, проверка формата. Одноразовые домены не блокируются.
- **Лимиты** (на существующем `createRateLimiter`):
  регистрация — 5/час с IP и 3/сутки на почту; письма — 3/час на почту и 10/час с IP;
  вход — как сейчас по IP плюс 10 за 10 минут на аккаунт (чтобы не перебирали один аккаунт с разных IP).
- **Сессии.** При входе, подтверждении почты всегда создаётся новая сессия. `last_seen_at` обновляется
  не чаще раза в 10 минут.
- **Токен-ссылки:** `PUBLIC_URL + /account#verify=<token>` и `#reset=<token>`. Фрагмент не попадает в логи nginx
  и в `Referer`; страница сразу стирает его из адресной строки.
- **Права.** `can()` по-прежнему возвращает `true` только для `admin`; `capabilities(user)` для `user` — все
  `false`. Место для этапов C и B — в `can()`, `capabilities()`, `featureFilter()`.

## Почта

`server/mailer.js` с единственным методом `send({ to, subject, text })`. Реализации:
- `smtp` — боевая;
- `log` — пишет письмо в консоль (разработка);
- `memory` — складывает в массив (тесты).

**SMTP-клиент:** неявный TLS на 465, `AUTH PLAIN`, одно письмо на соединение, таймауты 10 с на соединение и
20 с на отправку, проверка сертификата включена. STARTTLS/587 не поддерживается в v1.

**Письмо:** `text/plain`, UTF-8, `Content-Transfer-Encoding: base64`, тема в `=?UTF-8?B?…?=`. Значения заголовков
не содержат `\r`/`\n`. Тексты на русском: что за сайт, ссылка, срок действия, «если это были не вы, ничего не делайте».

**Сбои.** Отправка идёт в фоне; ошибка логируется без токена; регистрация не падает. Пользователь может нажать
«Выслать ещё раз». Если `MAIL_MODE` не настроен, при старте пишется предупреждение, а `register`,
`resend-verification` и `forgot-password` отвечают 503.

**Конфиг (env, `server/config.js`):** `MAIL_MODE` (`smtp`|`log`), `SMTP_HOST`, `SMTP_PORT` (по умолчанию 465),
`SMTP_USER`, `SMTP_PASS`, `MAIL_FROM`, `PUBLIC_URL`. Пароль SMTP лежит в `EnvironmentFile` systemd-юнита
с правами 0600 и не попадает в репозиторий.

## Безопасность

- Токены: 32 случайных байта; проверка — атомарный `UPDATE … WHERE used_at IS NULL AND expires_at > ?`,
  успех только у одного из параллельных запросов.
- Токены, пароли и тела писем не логируются.
- Пользовательский текст на страницах выводится только через `textContent`.
- IP клиента берётся из `X-Forwarded-For`, который nginx перезаписывает на `$remote_addr`
  (`server/deploy/nginx-map.conf`), поэтому лимиты по IP не обходятся подменой заголовка.
- Админ: вход, лимиты и cookie без ослабления.
- 152-ФЗ: чекбокс согласия на форме регистрации и страница `/privacy` (заготовка: какие данные — логин, почта,
  IP и устройство сессий; зачем; как запросить удаление). Юридическую правку делает владелец сайта.

## Интерфейс

**Страница `/account`** (`account.html`, `account.js`, `account.css`), самодостаточная, без фреймворков.
Состояния выбираются по фрагменту URL и ответу `/api/me`:

| Состояние | Содержимое |
|---|---|
| Гость | Вкладки «Вход» и «Регистрация», «Забыли пароль?» |
| Регистрация | Логин, почта, пароль и повтор, чекбокс согласия, скрытая ловушка |
| «Проверьте почту» | Кнопка «Выслать ещё раз» с таймером 60 с |
| `#verify=…` | Подтверждение, затем вход и профиль; при устаревшей ссылке — «Выслать новую» |
| `#reset=…` | Форма нового пароля, затем возврат к форме входа |
| Вошёл | Профиль (логин, почта, дата), смена пароля, список сессий, «Выйти» |

Поведение форм: блокировка кнопки на время запроса, ошибки под полем, 429 → «Слишком много попыток»,
корректные `autocomplete`, адаптив под телефон.

**Остальной сайт.**
- `account-nav.js` (~40 строк) показывает в шапке «Войти» или логин со ссылкой на `/account`;
  подключён **только в `index.html`**. На `index.html` заодно появляется ссылка на `/map`.
- На `map.html` `account-nav.js` не подключается: кнопка `#auth-btn` использует уже полученный `/api/me`.
  Диалог входа в `map.html` удалён. Кнопка ведёт на `/account?next=/map`; `next` принимается только как
  относительный путь, начинающийся с `/` и не с `//`. На телефоне кнопка входа на карте теперь видна.
- Яндекс.Метрика на `/account` без вебвизора (на странице формы с паролями).
- nginx: `location = /account` → `account.html`, `location = /privacy` → `privacy.html`; лимит `limit_req`
  (зона `anoma_register`) на `/api/register`, `/api/forgot-password` и `/api/resend-verification` рядом с `anoma_login`.

## Тесты

`node --test server/test/*.test.js tools/*.test.js`, без новых зависимостей:
- **Миграция:** пустая БД и БД «как на проде» приходят к одной схеме; `admin` подтверждён и входит; повтор безвреден.
- **Регистрация/подтверждение** через `memory`-почту: полный путь; вход до подтверждения; занятые логин
  (без учёта регистра), почта, зарезервированные имена; ловушка не создаёт аккаунт.
- **Токены:** одноразовость, срок, отзыв прежнего, параллельное использование проходит ровно один раз.
- **Сброс и смена пароля:** сессии закрыты (при смене текущая остаётся); одинаковые ответы для известной
  и неизвестной почты.
- **Лимиты:** регистрация, письма, перебор одного аккаунта с разных IP.
- **Сессии:** список, завершение своей, «все кроме этой», чужую завершить нельзя.
- **Права:** у `user` `capabilities` все `false`, запись карты — 403; `admin` не затронут.
- **Очистка:** неподтверждённые аккаунты и старые токены удаляются, подтверждённые и живые — нет.
- **Mailer:** кодирование, защита от `\r\n`; поддельный TLS-SMTP-сервер для диалога и таймаутов.

Страница `/account` проверяется вручную локально с `MAIL_MODE=log`.

## Деплой и раскатка

1. Бэкап БД, затем деплой кода. Миграция выполняется сама при старте `anoma-api`.
2. Пока `MAIL_MODE` не настроен, регистрация отвечает 503, а вход админа и карта работают как раньше.
3. Подготовка владельцем: почтовый ящик `noreply@anoma-wiki.ru` у провайдера (Beget; SPF/DKIM ведёт Beget),
   SMTP-данные в `EnvironmentFile` на VPS. Пошаговая инструкция — в `RELEASE.md`.
4. После настройки почты — проверочная регистрация на проде и проверка попадания письма во «Входящие».
5. В `CLAUDE.md` обновляется раздел «Статус проекта».

## Известные ограничения

Приняты сознательно: ~10 неудачных входов в один аккаунт за 10 минут блокируют вход в него на 10 минут (лимитер
по аккаунту); остаточная двухшаговая проверка существования почты (свежий логин с почтой X, затем тот же логин с
другой почтой: 409 только если X была свободна) ограничена лимитами регистрации, настоящее исправление требует
отложенного создания аккаунта; `cli.js set-password` не аннулирует выданные токены сброса; `/privacy` — заготовка
для владельца и юриста; браузерные сценарии (вёрстка на 375 px, стирание фрагмента, возврат по `next`)
автоматикой не кликались — перед анонсом нужен ручной проход.

## Вне объёма этапа A

Смена почты; самостоятельное удаление аккаунта; самообслуживание смены пароля админа (для него есть команда
`cli.js set-password <login>` с `ANOMA_PASSWORD` в окружении, закрывающая все сессии пользователя); вход через Telegram/VK/Discord; 2FA; аватары и публичные
профили; баннер cookie; блокировка одноразовых доменов; STARTTLS/587. Этапы C (личные метки) и B (предложения
с модерацией) — отдельные спеки и планы.
